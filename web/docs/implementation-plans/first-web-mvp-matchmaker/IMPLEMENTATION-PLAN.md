# Первый веб-MVP Matchmaker

## Summary

Создать русскоязычное React + TypeScript приложение в web на Vite. Реализовать восемь пользовательских страниц, публичный 404 и локальную mock-авторизацию, которую позднее можно заменить FastAPI-реализацией без изменений UI и маршрутизации.

## Implementation Changes

- Настроить Vite с `@vitejs/plugin-react`, React Router, Zod, Vitest, jsdom и React Testing Library (`user-event`, `jest-dom`); использовать npm и описать команды запуска и тестирования в README.
- Добавить публичные маршруты `/`, `/login`, `/register`, `*` и защищённые `/feed`, `/projects`, `/profile`, `/matches`, `/chat/:matchId`. Стартовая страница, вход, регистрация и 404 находятся вне `AppLayout`.
- Оформить страницы входа и регистрации через общий двухпанельный layout: презентационная панель занимает 50% desktop-экрана слева, форма — 50% справа; на мобильных презентационная панель скрывается, остаётся только форма.
- Создать `AppLayout` только для защищённых страниц: сворачиваемый sidebar, активная навигация и кнопка выхода. На desktop sidebar раскрывается при наведении, а на mobile используется нижняя навигация с отдельной кнопкой Menu для открытия полного sidebar.
- Использовать единый компонент-заглушку для защищённых разделов: название, краткое описание и статус «В разработке». Страница чата отображает `matchId`, без реализации чата и другой бизнес-логики.
- Разделить модели формы и сервиса:
  - `CredentialsInput`: email и пароль для `login` и `register`;
  - `RegisterFormInput`: email, пароль и `confirmPassword` только для UI-формы;
  - общая Zod-схема валидирует email и пароль, а схема формы дополнительно проверяет совпадение паролей.
- Определить асинхронный контракт `AuthService`:
  - `register(input): Promise<User>`;
  - `login(input): Promise<User>`;
  - `logout(): Promise<void>`;
  - `getCurrentUser(): Promise<User | null>`.

  Сервис возвращает публичный `User` без пароля и использует предсказуемые типизированные ошибки: дубликат email, неверные учётные данные и недоступное хранилище.
- Реализовать `mockAuthService` как единственное место доступа к `localStorage`, без модульного кэша. Использовать отдельные версионированные ключи для пользователей и сессии; сессия содержит только `userId`.
- Нормализовать email через `trim().toLowerCase()` до валидации, проверки дублей, входа и сохранения. Базовую Zod-валидацию применять также внутри сервиса, а не только в форме.
- Повреждённые данные в storage или сессия с несуществующим `userId` очищаются и трактуются как гостевая сессия. Ошибка доступа к `localStorage` преобразуется в ошибку сервиса, которую форма может показать пользователю.
- `AuthProvider` асинхронно восстанавливает сессию, хранит `user` и `isInitialized`, обновляет состояние после операций сервиса и не выполняет навигацию. Если доступ к storage недоступен при инициализации, провайдер завершает инициализацию, считает пользователя гостем и отдаёт ошибку в UI, не зависая в промежуточном состоянии.
- Регистрация сразу создаёт сессию и переводит пользователя в авторизованное состояние.
- Пока `isInitialized === false`, `ProtectedRoute` не перенаправляет пользователя. После инициализации гость перенаправляется на `/login`, сохраняя в router state полный внутренний URL: pathname, search и hash.
- После входа форма возвращает пользователя только на валидный внутренний URL из state; иначе направляет на `/feed`. Валидным считается только внутренний путь, начинающийся с `/`, без схемы, хоста и внешнего адреса. Авторизованный пользователь на `/login` и `/register` перенаправляется на `/feed`.
- Выход остаётся чистой операцией сервиса; после успешного `await logout()` защищённый маршрут перенаправляет пользователя на `/login` с `replace`.
- Формы используют корректные `type` и `autocomplete`, показывают inline-ошибки под соответствующими полями с красной обводкой и `aria-invalid`, а также блокируют повторную отправку на время запроса. Для неверной пары credentials используется безопасное сообщение «Неверный email или пароль» без раскрытия конкретного неверного значения.
- Хранение паролей в открытом виде явно обозначить в README как ограничение исключительно mock-MVP, недопустимое для production.

## Test Plan

- Проверить все публичные, защищённые и неизвестный маршруты, включая отсутствие `AppLayout` на `/`, `/login`, `/register` и 404.
- Проверить deep-link гостя `/chat/abc?tab=info#messages` → вход → возврат на полный исходный URL.
- Проверить клиентскую и сервисную валидацию, автоматический вход после регистрации, дубликаты email в разном регистре, успешный и ошибочный логин.
- Проверить выход: удаление сессии, переход на `/login` и повторную защиту маршрутов.
- Перед каждым тестом очищать `localStorage`; восстановление сессии проверять новым монтированием `AuthProvider`, а не только `rerender`.
- Проверить повреждённые данные storage, сессию с неизвестным `userId` и ошибку недоступного storage.
- Вручную проверить desktop и mobile: доступность форм, focus-состояния, активную навигацию и отсутствие горизонтального переполнения.

## Assumptions

- В web пока нет реализации, приложение создаётся с нуля.
- В MVP не входят FastAPI/JWT, подтверждение email, роли, onboarding, I18n, реальная лента, проекты, мэтчи и чат.
- При подключении API заменяется только реализация `AuthService`; UI, роутинг и `AuthProvider` сохраняют контракт.
