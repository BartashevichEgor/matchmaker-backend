## 1. Протокол Sprint Review

### 1.1. Что готово и что не готово

Владелец продукта представил цели спринта: подготовить понятный пользовательский сценарий входа и регистрации, создать дизайн основных экранов, спроектировать хранилище данных и контракт взаимодействия клиентов с сервером.

**Готово к демонстрации:**

1. В Figma подготовлены экраны загрузки, входа, регистрации, подтверждения e-mail и состояния ошибок для mobile, tablet и desktop.
2. Вероника подготовила экраны профиля и каталога. Это даёт основу для следующих пользовательских сценариев: заполнение своей анкеты, просмотр участников и поиск проекта или команды.
3. В backend реализованы и документированы системные endpoints `/ping`, `/health`, интерактивная Swagger-документация `/docs`, REST API с префиксом `/api/v1`, регистрация, подтверждение e-mail кодом, вход, восстановление пароля, JWT access/refresh, профиль, навыки, проекты, рекомендации, свайпы и matches.
4. Схема БД реализована моделями SQLAlchemy и Alembic-миграциями. В ней есть пользователи, профили, роли, навыки, связи компетенций, проекты, свайпы, matches, сессии и e-mail коды. По прототипу добавлен обязательный уникальный `username` для регистрации и карточек каталога.
5. Подготовлен контракт авторизации для клиентов: username, e-mail, пароль, повтор пароля, шестизначный код подтверждения и ожидаемые HTTP-статусы для ошибок.
6. Роман подготовил макеты и вёрстку страниц по дизайну, а также точки интеграции с API.
7. Алина подготовила вёрстку экранов входа и регистрации в KMP и тесты JSON-логики этих сценариев.

**Не считается завершённым в этом спринте:**

1. Полноценная реализация React-клиента не находится в репозитории `web`, поэтому её нельзя демонстрировать как готовую функциональность.
2. Node.js WebSocket-чат, реальная интеграция чата с match и сохранение сообщений ещё не готовы.
3. KMP-экраны ещё необходимо подключить к фактическому REST API. Минимальная длина пароля на клиенте должна быть синхронизирована с backend: 8 символов.
4. Публичный VPS, домен, HTTPS и реальная отправка почты не развёрнуты. Локально письмо сохраняется в outbox, а Docker Compose описан, но Docker Desktop на рабочем ПК не установлен.

### 1.2. Обсуждение результата командой разработки

Команда отметила, что в спринте удалось связать дизайн с техническими решениями. Экран регистрации теперь требует `username`, как в макете; backend хранит это значение, гарантирует его уникальность и передаёт в публичный профиль. Это устраняет расхождение между формой регистрации и каталогом пользователей.

Для авторизации принят единый сценарий: регистрация → код на e-mail → подтверждение e-mail → вход → получение JWT. Backend возвращает `422` для неверных данных формы, `409` для занятого e-mail или username, `401` для неверной пары логин/пароль и `403`, если e-mail ещё не подтверждён. Такие статусы позволяют React и KMP показать предусмотренные макетами ошибки у поля и экран «Нет подключения» при сетевом сбое.

Также команда зафиксировала, что демонстрационный HTML-экран backend не заменяет полноценный web-клиент Романа. Он нужен для проверки API и визуального сценария до интеграции двух отдельных клиентов.

### 1.3. Демонстрация готового инкремента

На Sprint Review команда демонстрирует следующие пункты:

1. Открытие `GET /health` и Swagger UI `/docs`.
2. Регистрацию нового пользователя с username, e-mail, паролем и повтором пароля.
3. Получение шестизначного кода из локального outbox, подтверждение e-mail и успешный вход.
4. Ответы API при неверном e-mail, коротком пароле, несовпадающих паролях, занятом username и неверном пароле.
5. Миграцию базы данных, таблицу `users` с уникальным `username`, а также ER-схему сущностей.
6. Экраны Figma: Loading, Login, Register, подтверждение e-mail, ошибки для mobile/tablet/desktop, профиль и каталог.
7. KMP-экраны входа и регистрации, подготовленные Алиной, и тесты JSON-логики.
8. Вёрстку страниц и подготовленные Романом API-точки интеграции.

### 1.5. Что команда будет делать дальше

Команда договорилась считать завершённой задачу только тогда, когда есть код, проверка и ссылка на подтверждающий артефакт в Product Board. Для backend критерием готовности являются миграция, тесты, Swagger и работающий сценарий; для UI — ссылка на Figma или исходный код, адаптивное состояние и обработка ошибок; для клиента — фактический запрос к API, а не только статичная вёрстка.

### 1.6. Изменения на рынке и в контексте продукта

Команда обсудила, что идея ориентирована на студентов, которым нужно быстро найти участников с недостающими компетенциями для учебного проекта или хакатона. Поэтому важны прозрачные навыки, понятное назначение профиля, подтверждение e-mail и мобильный сценарий. Формального исследования рынка в спринте не проводилось; этот вывод является рабочей гипотезой продукта, а не подтверждённой аналитикой. На следующем периоде стоит проверить её коротким опросом потенциальных студентов и уточнить, какие фильтры, роли и способы связи им действительно нужны.

### 1.7. Сроки, бюджет и прогноз релиза

Проект учебный, отдельный денежный бюджет не утверждался. Ограничение проекта — доступное время участников до защиты. С учётом готового дизайна, контракта API и backend-инкремента команда прогнозирует, что следующий инкремент должен быть посвящён интеграции клиентов с backend и чату, а не созданию новой несогласованной функциональности.

Риск прогноза: текущие репозитории не подтверждают готовую реализацию web-клиента и WebSocket-чата, а внешний VPS пока отсутствует. Поэтому демонстрация локального API возможна, но публичную ссылку на продукт нельзя обещать до фактического развёртывания.

## 3. Протокол Sprint Retrospective

### 3.1. Что было хорошо

**Люди и взаимодействия.** Команда распределила зоны ответственности: дизайн и документация, web и чат, KMP и backend. Макеты авторизации были доведены до состояний ошибок, благодаря чему backend смог зафиксировать точные требования к полям и HTTP-ответам.

**Процессы.** Для backend появились понятные артефакты: миграции, Swagger, README, тесты, линтер и локальные скрипты запуска. Это снижает зависимость от устных объяснений и позволяет коллегам самостоятельно проверить API.

**Инструменты.** FastAPI автоматически публикует OpenAPI и Swagger; SQLAlchemy и Alembic сохраняют схему БД в коде; pytest проверяет ключевые сценарии. Проверка прошла на SQLite и PostgreSQL. Для авторизации выбран безопасный минимум: Argon2-хеширование паролей, e-mail коды, access/refresh JWT и отзыв сессий.

**Критерии готовности.** Для backend удалось определить проверяемые условия: миграция применяется на пустой БД, endpoint виден в Swagger, тест проходит, в логах нет паролей и JWT. Это хороший шаблон для остальных карточек.

### 3.2. Предложения по улучшению

1. Перед началом каждой задачи записывать в карточке критерии готовности, ссылку на макет или API-метод и способ проверки.
2. Использовать один контракт `docs/figma-auth-contract.md` для React и KMP, чтобы длина пароля, username и тексты ошибок не расходились.
3. Проводить короткую интеграционную проверку раз в неделю: один пользователь проходит register → verify → login на каждом клиенте.
4. Явно фиксировать story points, план/факт времени и статус Done на Product Board. Это позволит оценивать velocity без догадок.
5. Не записывать статичную вёрстку как готовую клиентскую функцию, пока она не вызывает API и не обрабатывает реальные ответы.
6. Сначала согласовать протокол WebSocket-чата, затем писать клиент и сервер чата параллельно.
7. Выделить отдельную карточку на Docker Desktop/VPS/SMTP и не считать деплой завершённым до проверки по публичному адресу.

### 3.3. Что было плохо и чего избегать дальше

1. Требование `username` оказалось в макете позже, чем в исходной backend-схеме. Это вызвало расхождение между формой регистрации и API. Исправлено миграцией, но подобные поля надо утверждать до создания БД.
2. В KMP первоначально была минимальная длина пароля 6, а сервер требует 8. Клиентская и серверная валидация должны проверяться на одной тестовой таблице до начала интеграции.
3. В репозитории web пока нет исходного React-кода, поэтому невозможно подтвердить завершённость фронтенд-задач только по словам или макетам.
4. Docker на рабочем компьютере не установлен, а VPS ещё не выдан. Нельзя указывать контейнерный или удалённый деплой как фактически выполненный до реального запуска.
5. Отсутствие заполненных SP и трудозатрат в Product Board не позволяет честно рассчитать производительность команды. В следующем спринте каждую карточку нужно оценить до старта и закрывать с фактическим временем.
