# Backend Matchmaker: подробный конспект и инструкция для Егора

> Этот файл объясняет направление Backend & DevOps с нуля: что делает каждый слой, где он находится, как запустить проект, как проверить результат и как объяснить его преподавателю. Команды ниже рассчитаны на Windows PowerShell и выполняются из корня репозитория `matchmaker-backend`.
>
> Актуально для текущей реализации: FastAPI, PostgreSQL, SQLAlchemy 2.0, Alembic, JWT, Redis для лимитов, Docker Compose, pytest и Ruff.

## 1. Что мы разрабатываем

**Matchmaker** — платформа, на которой студент может заполнить профиль и навыки, найти проект по своим компетенциям, выразить интерес к проекту и получить `match`, если руководитель проекта тоже выбрал его. Руководитель проекта создаёт проект, задаёт нужные навыки и специализации, просматривает кандидатов и выбирает их. После взаимного выбора участник отдельно подтверждает вступление в проект; затем пара «проект — участник» может открыть общий чат.

Твоя зона как Lead Backend & DevOps — это не макеты экранов. Твоя задача — сделать надёжный сервер, который хранит данные, проверяет права, выдаёт JSON клиентам, рассчитывает рекомендации, документирован и воспроизводимо запускается.

### Что уже есть в текущем репозитории

- REST API FastAPI с интерактивной спецификацией Swagger на `/docs`.
- `/ping` и `/health` для быстрой проверки сервера.
- PostgreSQL-схема из SQLAlchemy-моделей и миграция Alembic.
- Регистрация, подтверждение email кодом, вход, JWT access/refresh, refresh rotation, выход и восстановление пароля.
- Анкета, роли, навыки с уровнями, проекты и модерация статусов.
- Рекомендации по косинусному сходству векторов навыков.
- Свайпы в обе стороны, match, защищённый доступ к данным чата и подтверждение вступления в проект.
- Логи запросов без паролей, тесты, Ruff, Dockerfile, docker-compose, GitHub Actions и README.

### Что пока не должно выдаваться за готовое

- В репозитории frontend папка `web` пока содержит только README: готового React-клиента там нет.
- iOS-проект содержит экраны входа и регистрации, но ещё не делает сетевые запросы к API.
- Отдельный Node.js WebSocket-чат пока не реализован; backend уже выдаёт `room_key`, который он должен использовать.
- Docker Compose описан, но Docker Desktop на этом компьютере не установлен, поэтому Compose здесь ещё не запускался.
- Внешний SMTP-провайдер, VPS, домен и HTTPS требуют реальных доступов и отдельного деплоя. Локальный режим вместо письма сохраняет код в `core-api/.local/outbox`.
- Redis подключается для распределённых лимитов запросов. Кэширование refresh-сессий в Redis не сделано: они намеренно хранятся в PostgreSQL, чтобы отзыв токенов был надёжным.

```text
matchmaker-backend/
├── core-api/                    # FastAPI-сервис
│   ├── app/
│   │   ├── api/                 # HTTP-маршруты: auth, profiles, projects и др.
│   │   ├── core/                # config, JWT/хеширование, лимиты
│   │   ├── services/            # scoring, email, преобразование моделей в ответы
│   │   ├── static/              # небольшая демонстрационная страница
│   │   ├── main.py              # создание FastAPI-приложения
│   │   ├── models.py            # SQLAlchemy-модели = описание таблиц
│   │   ├── schemas.py           # Pydantic-входы и ответы HTTP API
│   │   ├── db.py                # engine, сессии и Base
│   │   └── cli.py               # bootstrap, начальные справочники, make-admin
│   ├── migrations/              # история Alembic
│   ├── tests/                   # pytest-сценарии
│   ├── docs/                    # схема БД, API, сдача, этот конспект
│   ├── Dockerfile
│   ├── alembic.ini
│   ├── requirements.txt
│   └── requirements-dev.txt
├── chat-service/                # точка для отдельного сервиса Ромы
├── docker-compose.yml           # PostgreSQL + Redis + Mailpit + API
├── start.ps1                    # локальный запуск API
├── start-local-db.ps1           # отдельный локальный PostgreSQL
└── start-background.ps1         # сервер в фоне
```

Главное правило структуры: **маршрут не должен содержать всю логику приложения**. В `api/` остаётся перевод HTTP-запроса в вызовы к БД и сервисам, модели описывают данные, Pydantic проверяет внешний JSON, а `services/` содержит вычисления и представления.

## 3. Сначала пойми базовые понятия

### 3.1 Python и виртуальное окружение

Python запускает код интерпретатором. Модули сторонних библиотек не нужно ставить глобально в Windows: они устанавливаются в папку виртуального окружения `.venv`. Тогда у каждого репозитория свои версии FastAPI, SQLAlchemy и тестов.

```powershell
cd C:\ФПМИ\ТП\matchmaker-backend-new
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r core-api\requirements-dev.txt
```

Почему команда использует `python -m pip`, а не просто `pip`: она гарантированно устанавливает пакеты именно для выбранного Python из `.venv`.

Проверка:

```powershell
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip show fastapi
```

Не добавляй `.venv`, `.env`, локальную базу или письма в Git. `.gitignore` уже исключает их.

### 3.2 HTTP, REST и JSON

Клиент и сервер общаются HTTP-запросами. У запроса есть:

- **метод**: `GET` читает, `POST` создаёт, `PUT` заменяет, `PATCH` меняет часть, `DELETE` удаляет;
- **URL**: например `/api/v1/projects/42`;
- **заголовки**: например `Authorization: Bearer <access token>`;
- **JSON-тело** у запросов, которые передают данные;
- **статус ответа**: `200` успешно, `201` создано, `401` нет валидного входа, `403` нет права, `404` не найдено, `409` конфликт, `422` данные не прошли валидацию.

REST — соглашение организовывать URL вокруг ресурсов. `GET /projects` получает список, `POST /projects` создаёт проект, `GET /projects/42` читает один проект. В API Matchmaker все рабочие ресурсы имеют префикс `/api/v1`; `v1` позволит позднее выпустить несовместимую версию без поломки старых клиентов.

Пример запроса регистрации:

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "username": "egor.dev",
  "email": "egor@example.com",
  "password": "correct-horse-2026"
}
```

### 3.3 FastAPI и Pydantic

FastAPI создаёт сервер и OpenAPI-описание из обычных Python-функций. Декоратор сообщает: «когда придёт `GET /ping`, вызови эту функцию».

```python
@app.get("/ping")
def ping():
    return {"message": "pong"}
```

Pydantic-модель описывает допустимый JSON. В `schemas.py` модель `Register` требует уникальное публичное имя длиной 1–50 символов, корректный email и пароль длиной 8–128 символов. React сверяет два поля пароля до отправки; другие клиенты могут передать `password_confirm` или `confirmPassword` для дополнительной серверной сверки. Если пользователь прислал неверные данные, FastAPI не запускает бизнес-логику и возвращает `422`.

Это важно: браузерная проверка формы улучшает интерфейс, но **защитой является проверка на сервере**. Любой клиент можно обойти, отправив HTTP вручную.

### 3.4 PostgreSQL, SQL и ORM

Реляционная БД хранит данные в таблицах. Строка `users` — пользователь, строка `profiles` — одна анкета пользователя. Связь задаётся внешним ключом: `profiles.user_id` ссылается на `users.id`. `UNIQUE` не даёт зарегистрировать один email дважды; составной первичный ключ `profile_skills(profile_id, skill_id)` не даёт повторить один навык в анкете.

Пример чистого SQL:

```sql
SELECT u.email, p.first_name
FROM users AS u
JOIN profiles AS p ON p.user_id = u.id
WHERE u.is_verified = true;
```

SQLAlchemy ORM позволяет выражать то же самое Python-классами. `class User(Base)` описывает таблицу `users`, а `User(email=...)` — будущую строку. ORM удобен, но не отменяет знание SQL: надо понимать индексы, JOIN, транзакции, внешние ключи и последствия запросов.

### 3.5 Миграции Alembic

Схема БД — часть программы. Нельзя полагаться на ручное создание таблиц у каждого разработчика. Alembic хранит историю изменений в файлах миграций: первая версия в `migrations/versions/0e5a5b1319e6_initial_matchmaker_schema.py`.

```powershell
cd core-api
..\.venv\Scripts\python.exe -m alembic upgrade head
```

Команда применяет все миграции, которых ещё нет в таблице `alembic_version`. Когда модель меняется, алгоритм такой:

1. Измени `app/models.py`.
2. Сгенерируй черновик: `python -m alembic revision --autogenerate -m "add field"`.
3. Прочитай миграцию вручную: autogenerate не знает бизнес-смысл.
4. Примени её к пустой тестовой БД.
5. Выполни `python -m alembic check` и тесты.
6. Закоммить модель и миграцию вместе.

Никогда не переписывай уже опубликованную миграцию, если её успели применить другие люди или сервер. Создай следующую.

### 3.6 JWT, хеширование и email-код

Пароль нельзя хранить как обычный текст. `pwdlib` с Argon2 превращает пароль в соль + хеш. При входе библиотека проверяет пароль против хеша; сервер не восстанавливает исходную строку.

JWT — подписанный сервером документ. Access token короткий (15 минут) и кладётся в `Authorization`. Refresh token действует дольше, но после каждого применения его сессия отзывается и выдаётся новый токен. Поэтому украденный старый refresh token нельзя использовать бесконечно.

Шестизначный email-код тоже не хранится открыто: в БД лежит HMAC digest, срок действия, цель (`verify` или `reset`) и число ошибок. Код одноразовый и действует 10 минут.

### 3.7 Косинусное сходство

Навык — координата вектора. Если справочник имеет Python, React, PostgreSQL, анкета может быть `[5, 0, 4]`, а проект `[3, 0, 5]`. Косинусное сходство:

```text
score = (a · b) / (||a|| × ||b||)
```

где `a · b` — скалярное произведение. Значение от 0 до 1 показывает близость направления навыков; это не гарантирует успешность команды и не является процентом «профпригодности». Если у кого-то нет навыков, длина вектора равна нулю, поэтому score принимается равным 0, чтобы не делить на ноль.

В реализации ось — ID навыка из общего справочника. У пользователя значение `level`, у проекта — `weight`. Функция лежит в `app/services/scoring.py`; тесты проверяют обычные, ортогональные и нулевые векторы.

## 4. Пошаговый запуск с нуля

### Шаг 1. Получи репозиторий и зависимости

```powershell
git clone https://github.com/BartashevichEgor/matchmaker-backend.git
cd matchmaker-backend
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r core-api\requirements-dev.txt
```

Если `py` не найден, проверь установку Python: `py --version`. Если `git` не найден, поставь Git for Windows и открой новое окно PowerShell.

### Шаг 2. Создай локальную конфигурацию

`start.ps1` сам создаёт `core-api/.env` с безопасным случайным JWT-секретом, если файла нет. Он же применяет миграции и добавляет справочники. Поэтому обычно достаточно:

```powershell
.\start.ps1
```

Вручную тот же процесс выглядит так:

```powershell
cd core-api
..\.venv\Scripts\python.exe -m app.cli bootstrap
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

`--reload` удобен только при разработке: Uvicorn перезапускает процесс после изменения Python-файла. В production его не используют.

### Шаг 3. Проверь сервер

Открой в браузере:

- `http://127.0.0.1:8000/` — демонстрационная страница;
- `http://127.0.0.1:8000/docs` — Swagger UI;
- `http://127.0.0.1:8000/ping` — `{"message":"pong"}`;
- `http://127.0.0.1:8000/health` — состояние API и подключений.

Если видишь `ERR_CONNECTION_REFUSED`, это не ошибка страницы: сервер не запущен или терминал с Uvicorn закрыт. Запусти `start.ps1` и оставь его работать. Для фонового режима есть `start-background.ps1`, а его PID и логи лежат в `core-api/.local/`.

### Шаг 4. Выбери базу данных

Для быстрого старта без `DATABASE_URL` сервис использует SQLite. Для учебного требования PostgreSQL нужен один из двух путей:

1. **Отдельный локальный PostgreSQL проекта.** `start-local-db.ps1` поднимает изолированный экземпляр на `127.0.0.1:55432`, не трогая установленную Windows-службу PostgreSQL.
2. **Docker Compose.** Поставь и запусти Docker Desktop, скопируй `.env.example` в `.env`, задай `POSTGRES_PASSWORD` и `JWT_SECRET`, затем выполни `docker compose up --build -d`.

Проверка миграции:

```powershell
cd core-api
..\.venv\Scripts\python.exe -m alembic current
..\.venv\Scripts\python.exe -m alembic check
```

## 5. Как устроен API и что проверять вручную

### 5.1 Системные методы

| Метод | Смысл | Ожидаемый результат |
|---|---|---|
| `GET /ping` | процесс отвечает | `200` и `message: pong` |
| `GET /health` | проверка API/БД/Redis | `200`, `status: ok`, тип БД |
| `GET /docs` | локальный Swagger | экран документации без внешнего CDN |

### 5.2 Авторизация

1. `POST /api/v1/auth/register`: отправь `username`, email и пароль. Web-форма сверяет повтор пароля до отправки; иные клиенты могут дополнительно передать `password_confirm`.
2. В local режиме открой свежий `.txt` в `core-api/.local/outbox` и перепиши код. В Compose открой Mailpit: `http://localhost:8025`.
3. `POST /api/v1/auth/verify-email`: email + шестизначный code.
4. `POST /api/v1/auth/login`: email + пароль. Скопируй `access_token`.
5. В Swagger нажми **Authorize**, вставь access token без слова `Bearer`.
6. Выполни `GET /api/v1/users/me`.

Refresh token отправляется только в `POST /api/v1/auth/refresh` телом `{ "refresh_token": "..." }`. Он одноразовый: повтор того же вызова даёт `401`. `POST /api/v1/auth/logout` отзывает все сессии пользователя.

### 5.3 Профиль и компетенции

Сначала вызови `GET /api/v1/roles` и `GET /api/v1/skills`. Затем:

```json
PATCH /api/v1/profiles/me
{
  "first_name": "Егор",
  "last_name": "Барташевич",
  "bio": "Backend и DevOps",
  "github_url": "https://github.com/BartashevichEgor",
  "role_id": 1
}
```

Навыки заменяются одной операцией, а не добавляются по одному:

```json
PUT /api/v1/profiles/me/skills
{
  "skills": [
    { "skill_id": 1, "level": 5 },
    { "skill_id": 2, "level": 3 }
  ]
}
```

Список не должен содержать один ID дважды. Уровень всегда от 1 до 5. Дата рождения доступна владельцу анкеты, но не попадает в публичный профиль — это пример контроля приватности на уровне ответа API.

### 5.4 Проекты и рекомендации

Создать проект может подтверждённый пользователь. Владелец берётся из JWT, поэтому клиент не способен «назначить» другого владельца.

```json
POST /api/v1/projects
{
  "title": "Приложение для хакатона",
  "description": "Собираем сервис поиска команды для студенческого хакатона.",
  "skills": [
    { "skill_id": 1, "weight": 5 },
    { "skill_id": 2, "weight": 3 }
  ],
  "role_ids": [1, 2]
}
```

`GET /api/v1/recommendations/projects` возвращает открытые чужие проекты, отсортированные по score. Владелец проекта вызывает `GET /api/v1/projects/{id}/recommendations/candidates`. Фильтры по навыку и роли доступны в каталоге проектов, а role_id доступен и в рекомендациях.

### 5.5 Свайпы, match и чат

Соискатель ставит реакцию проекту:

```json
PUT /api/v1/projects/{project_id}/my-swipe
{ "decision": "like" }
```

Владелец проекта ставит реакцию конкретному кандидату:

```json
PUT /api/v1/projects/{project_id}/candidates/{candidate_id}/swipe
{ "decision": "like" }
```

Когда существуют оба like, появляется одна запись `matches`. Уникальные ограничения БД и блокировка проекта на PostgreSQL защищают от двойного match при параллельных запросах. Повтор одного и того же PUT безопасен: это свойство называется **идемпотентность**.

`GET /api/v1/matches/{match_id}/chat-access` проверяет, что запрос делает только кандидат или владелец проекта, и выдаёт match с `room_key`. Node.js-сервис чата должен принимать access JWT, проверять доступ через этот endpoint или общую проверку подписи и использовать `room_key` как идентификатор комнаты. Реальный WebSocket-сервер пока должен сделать Рома.

## 6. Принятые решения по базе данных

Смотри полную Mermaid ER-диаграмму в [database.md](database.md). Ключевые таблицы:

- `users`: учётная запись, email, хеш, флаги подтверждения/админа.
- `profiles`: один-к-одному с пользователем, имя, опыт, GitHub, роль.
- `skills`, `roles`: справочники. Роль — специализация (Backend, Frontend), а не право администратора.
- `profile_skills`: M:N между анкетой и навыком с уровнем.
- `projects`: объявление проекта и его владелец.
- `project_skills`, `project_roles`: требования проекта.
- `swipes`: решения `like/pass` в каждом направлении.
- `matches`: уникальная пара проекта и кандидата.
- `project_members`: участник, который подтвердил вступление.
- `email_codes`, `refresh_sessions`: временные данные безопасности.

Почему не хранить навыки строкой через запятую в `users`? Тогда нельзя сделать внешний ключ, избежать опечаток, нормально фильтровать и строить вектор. Отдельный справочник делает данные согласованными.

## 7. Тесты, линтер и логи

### Тесты

```powershell
cd core-api
..\.venv\Scripts\python.exe -m pytest -q
..\.venv\Scripts\python.exe -m scripts.test_postgres
```

Первый запуск использует изолированную SQLite-тестовую БД, второй поднимает временную PostgreSQL-БД с уникальным названием, запускает тесты и удаляет только её. В тестах проверяются регистрация, дубли email, коды, refresh replay, logout, права администратора, приватность профиля, cosine score, рекомендации, модерация, Swagger и параллельные запросы.

Тест проверяет наблюдаемое требование. Например, вместо теста «функция была вызвана» важнее проверить: нельзя использовать refresh token второй раз и нельзя прочитать чужой match.

### Ruff

```powershell
..\.venv\Scripts\python.exe -m ruff check .
..\.venv\Scripts\python.exe -m ruff format --check .
```

Ruff ищет распространённые ошибки Python и нарушенный порядок импортов. Он не заменяет ревью логики и тесты.

### Логи

`main.py` присваивает каждому запросу уникальный request ID и пишет метод, путь, статус и длительность. Пароль, JWT и тело запроса в лог не записываются. При `500` клиент видит нейтральное сообщение и request ID, а не внутреннюю трассировку или секреты.

## 8. Docker и production

### Локальный Compose

В корне:

```powershell
Copy-Item .env.example .env
# В .env укажи POSTGRES_PASSWORD и JWT_SECRET длиной не меньше 32 символов.
docker compose up --build -d
docker compose ps
docker compose logs api
docker compose down
```

Compose запускает API, PostgreSQL 16, Redis 7 и Mailpit. БД и Redis не публикуются наружу; API и Mailpit привязаны к localhost. `docker compose down` останавливает контейнеры, но не удаляет named volumes. Не используй `down -v`, если в них есть нужные данные.

### Что нужно для VPS

1. Сервер Linux с обновлениями, Docker Engine/Compose и закрытым доступом к Postgres/Redis извне.
2. Домен и reverse proxy (например Nginx или Caddy) с HTTPS.
3. Настоящие переменные окружения: надёжные `JWT_SECRET`, `POSTGRES_PASSWORD`, Redis URL, SMTP.
4. Backup PostgreSQL, журналы и мониторинг health endpoint.
5. Deploy из проверенного образа или GitHub Actions. После deploy повторить регистрацию, email, логин, профиль, проект, match.

Нельзя утверждать, что VPS развёрнут, пока нет реального адреса и результата проверки.

## 9. Контракт с коллегами

### Рома, web и чат

На момент проверки в `matchmaker-frontend/web` нет исходного React-приложения. Когда оно появится, базовый URL для разработки — `http://127.0.0.1:8000/api/v1`, а CORS допускает Vite origins `localhost:5173` и `127.0.0.1:5173`. Использовать надо именно OpenAPI на `/openapi.json`, а не угадывать названия полей.

Для чата нужно согласовать протокол с Ромой: адрес Socket.IO, способ передать access token, событие входа в `room_key`, формат сообщения и кто хранит историю. До этого backend намеренно не имитирует WebSocket.

### Алина, iOS

В KMP есть статичные `LoginScreen` и `RegisterScreen`: их кнопки пока не вызывают API. Экран регистрации сейчас проверяет пароль минимум 6 символов, а сервер требует минимум 8. Перед подключением клиент нужно изменить на «не менее 8 символов», чтобы пользователь не получал неожиданное серверное `422`.

У iOS регистрации есть поле «Имя пользователя»; `/auth/register` теперь создаёт его как публичный уникальный `username`. Имя человека остаётся в профиле: register → verify email → login → `PATCH /profiles/me` с `first_name`. Так один и тот же контракт работает и для браузера, и для iOS.

На физическом телефоне `127.0.0.1` означает сам телефон, а не компьютер разработчика. Нужен IP компьютера в локальной сети, HTTPS стенд или туннель, а для iOS ещё настройки App Transport Security. Это не надо решать изменением backend endpoint.

### Вероника, документация и дизайн

Для отчёта можно взять [database.md](database.md) как ER-диаграмму и [api.md](api.md) как технический API-контракт. В Figma-интеграции на момент проверки доступ был ограничен политикой/лимитом среды, поэтому не делай вид, что конкретный слой макета автоматически проверен. ## 11. Частые проблемы и быстрые решения

| Симптом | Причина | Что сделать |
|---|---|---|
| `ERR_CONNECTION_REFUSED` | Uvicorn не запущен | Выполни `./start.ps1`, не закрывай терминал |
| `uvicorn: Missing argument APP` | Запущена только команда `uvicorn` | Запусти `python -m uvicorn app.main:app --app-dir core-api --reload` из корня |
| `ModuleNotFoundError` | Пакет поставлен не в `.venv` | Используй `.\.venv\Scripts\python.exe -m pip install -r ...` |
| `401` | Нет или истёк access token | Выполни login или refresh, затем отправь `Authorization: Bearer ...` |
| `403 Confirm your email first` | Email не подтверждён | Возьми код из outbox/Mailpit и вызови verify-email |
| `422` | JSON не соответствует Pydantic-схеме | Посмотри `detail` ответа и схему в Swagger |
| `409` при регистрации | Email уже существует | Войди в существующий аккаунт или используй другой test email |
| `alembic check` не проходит | Модели и миграции расходятся | Создай и проверь новую миграцию |
| Docker не найден | Docker Desktop не установлен/не запущен | Пока используй локальный PostgreSQL или установи Docker Desktop |

## 12. Минимальный чек-лист перед демонстрацией

1. `git status` пустой либо понятны все изменённые файлы.
2. Зависимости установлены в `.venv`.
3. `pytest -q`, PostgreSQL-тесты и Ruff успешно прошли.
4. `GET /health` возвращает `status: ok`.
5. Swagger открывается локально.
6. Проходится сценарий register → verify → login → profile → project → recommendation → like → match.
7. README не содержит пароли, токены, локальный `.env` или адреса персональной почты.
8. Для внешней сдачи готовы реальный URL, HTTPS и проверка на этом URL — либо честно указано, что VPS ещё не предоставлен.

Этот конспект не заменяет чтение кода. Хороший следующий шаг — открыть один маршрут, например `app/api/auth.py`, и последовательно проследить: Pydantic-вход → проверка → SQLAlchemy-модель → commit → Pydantic-ответ → тест.
